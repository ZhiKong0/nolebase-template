# 2026-03-26 控制调度重构与低速抖动根因修复

## 本次修改目标

- 将关键控制路径从“主循环追赶 `Control_Tick()`”改为“TIM4 严格定时调度”
- 避免主循环被 OLED、串口、按键、软 I2C IMU 读取拖慢后，控制周期失真
- 去除默认 `startup bias` 对低速区的非对称扰动
- 将 heading 闭环启用条件从内部 `pwmCore` 改为“实际速度进入可控区”

## 根因判断

### 1. 控制路径与后台任务耦合过深

原结构中：

- `Control_TimerTickISR()` 仅做部分速度环更新
- `Control_Tick()` 由主循环根据 `g_tim4PendingTicks` 追赶执行
- `Control_Tick()` 内同时承担：
  - 串口命令解析
  - IMU 读取与姿态更新
  - 遥测发送
  - 实验采样/流输出
  - 实验超时收尾

这会导致主循环一旦被阻塞，控制相关逻辑的实际执行时刻发生漂移，形成：

- 编码器采样不稳
- 姿态环节拍漂移
- 低速时反馈失真
- 车辆出现抖动和抽动

### 2. 低速区提前注入非对称补偿

原默认参数中：

- `STABLE_DEFAULT_STARTUP_BIAS_PWM = 3`

且 heading 闭环仅依赖 `pwmCore` 阈值启用。这样会在车辆尚未进入稳定滚动区时，提前注入左右不对称修正，导致低速时单轮容易被拉成反向或近反向输出。

## 本次代码修改

### 文件：`Hardware/Control.c`

#### 1. 默认关闭 startup bias

- `STABLE_DEFAULT_STARTUP_BIAS_PWM: 3 -> 0`

#### 2. heading 启用条件改为基于实际速度

- 从 `abs(pwmCore) >= HEADING_ENABLE_PWM_THRESHOLD`
- 改为 `abs(actualSpeed) >= speedIEnableSpeed`

目的：只有车辆实际进入可控移动状态后，才启用 heading 差分修正。

#### 3. 引入严格定时的角度环周期

新增：

- `ANGLE_LOOP_PERIOD_MS = 5`

并在 `Control_TimerTickISR()` 中直接按绝对 tick 触发：

- 速度环：10ms
- 角度环：5ms
- 实验采样：按 `expSamplePeriodMs`

#### 4. IMU 读取改为后台轮询 + 快照发布

新增后台函数：

- `control_poll_imu()`

职责：

- 在主循环后台读取阻塞式软 I2C IMU
- 更新 `sys->icm`
- 原子发布控制快照：
  - `sensedPitch`
  - `sensedYaw`
  - `sensedYawRate`

  - `imuDataValid`

#### 5. 角度环改为消费 IMU 快照

职责：

- 在 TIM4 严格节拍中运行
- 只消费后台已发布的 IMU 快照

#### 6. 后台逻辑与控制逻辑解耦

新增：

后台只负责：

- 串口命令处理

## 预期收益

### 1. 控制周期稳定

关键控制路径不再受主循环拥塞影响，编码器更新、角度环、电机输出具有稳定节拍。

### 2. 抖动根因减少

低速区不再默认引入 startup bias，heading 闭环也不再过早介入，能减少“左右轮在静摩擦区互相拉扯”的现象。

### 3. 结构更符合实时控制原则

- ISR：严格定时控制
- 主循环：非实时后台任务

这是比“主循环追赶控制”更符合实时系统第一性原理的结构。

## 风险与后续验证点

### 风险 1：IMU 快照刷新慢于角度环

如果后台 IMU 读取偶发失败，角度环会短时使用上一帧快照。该行为比“在 ISR 中阻塞读取 IMU”更安全，但需要关注连续失败时的姿态滞后。

### 风险 2：实验采样首包时间

实验采样当前由严格 tick 差分触发，首个样本时间可能不再恰好落在 `t_ms=0`，需结合上位机解析脚本确认是否接受。

### 风险 3：仍可能存在硬件层问题

若修改后仍有抖动，应继续重点检查：

- 编码器线束/接触
- `cl/cr` 是否仍频繁触发
- 机械启动阈值左右不一致

## 第四阶段根因收敛：起步前几拍双边同时反向输出

### 现象回放

新固件样本 `exp001_raw.txt` 中，起步早期出现了两次明显的双边同时反向：

- `HB tick=191525 ... ae=1.742 ao=-15.590 L=-16 R=-16 OL=-26 OR=-26`
- `HB tick=192297 ... ae=1.783 ao=-18.703 L=-18 R=-20 OL=-28 OR=-30`

关键特征：

- 左右同时为负，不是单轮差分反向
- `sbf=0`，说明不是 startup bias 导致
- `cl=0 cr=0`，说明不是编码器空窗或夹零导致
- `ae` 为正但 `ao` 为负，说明角度环输出存在控制理论层面的符号反转来源

### 根因定位

原代码角度环使用的是“对误差微分”：

```c
derivative = (sys->angleErr - sys->anglePrevError) / dt;
sys->angleOut = sys->angleKp * sys->angleErr + sys->angleKi * sys->angleI + sys->angleKd * derivative;
```

而当前结构中：

- 外环速度环会动态更新 `targetAngle`
- 起步阶段 `targetAngle` 会随着速度建立而快速变化

这意味着即使车身实际姿态没有出现对应幅度的反向运动，只要参考值 `targetAngle` 本身发生下降，就会让：

- `angleErr` 突然减小
- `d(angleErr)/dt` 变成一个很大的负值
- `Kd * derivative` 直接把 `angleOut` 拉成负

这就是典型的 **derivative kick（微分踢）**。

也就是说，当前双边同时反向输出的根因，不是机械、不是真实姿态反向，而是：

- **角度环把 D 项做在误差上，外环参考变化被错误地当成了被控对象的真实运动。**

### 修复原则

采用标准控制理论修复：

- 将角度环微分改为 **D on measurement**
- 只对 `actualAngle` 做微分，而不对 `targetAngle - actualAngle` 做微分

这样：

- 外环参考变化不会再触发内环 D 项踢动
- 只有真实姿态变化才会触发阻尼项

### 本次代码修改

#### 文件：`Hardware/Control.h`

新增状态：

- `anglePrevActual`

用于保存上一拍的实际姿态角。

#### 文件：`Hardware/Control.c`

原逻辑：

```c
derivative = (sys->angleErr - sys->anglePrevError) / dt;
sys->angleOut = sys->angleKp * sys->angleErr + sys->angleKi * sys->angleI + sys->angleKd * derivative;
```

新逻辑：

```c
derivative = (sys->actualAngle - prevActualAngle) / dt;
sys->angleOut = sys->angleKp * sys->angleErr + sys->angleKi * sys->angleI - sys->angleKd * derivative;
sys->anglePrevActual = sys->actualAngle;
```

同时在以下位置初始化 `anglePrevActual`：

- `control_reset_angle_loop()`
- `Control_Init()`
- `Control_Start()`

### 预期效果

修复后，起步阶段即使：

- `targetAngle` 因速度环建立而快速变化

角度环 D 项也不会再因为参考变化本身产生反向踢动。

预期直接改善：

- 起步前几拍双边同时反向输出消失或显著减少
- `ao` 不再在 `ae > 0` 时被突然拉成负值
- 起步动作更连续，整车不再出现“先猛退一下再前冲”的控制瞬态

## 第五阶段根因收敛：静止态 `yaw_jump` 与 BNO 姿态链路修复

### 新发现

在 `exp002` 末段，已经确认存在多次：

- `run=0`
- `L=0 R=0`
- `OL=0 OR=0`
- `el=0 er=0`

但 `yaw` 与 `yr` 仍然明显跳变的样本，例如：

- `tick=90040 y=30.841 yr=35.385`
- `tick=90442 y=8.992 yr=3.977`
- `tick=90844 y=-12.141 yr=-15.813`
- `tick=91480 y=2.406 yr=5.654`

这说明当前 `yaw_jump` 已不再优先指向电机控制输出，而是首先落在：

- BNO 姿态数据读取/解析链路
- `yaw` 连续性维护逻辑

### 根因 1：BNO 收包 payload 读取偏移错误风险

原 `BNO085_ReceivePacket()` 逻辑为：

- 先读 `4` 字节 header
- 再读 `len + 4` 字节
- 再把后一次读取结果的前 `4` 字节丢弃

该实现存在较高的 payload 错位或跨包污染风险，会直接影响：

- `reportId`
- 四元数 `q0/q1/q2/q3`
- 最终 `yaw`

本轮已改为：

- 先读 `4` 字节 header
- 再只读 `len` 字节 payload
- 直接拷贝到 `g_bnoData`

对应修复文件：`Hardware/ICM42688.c`

### 根因 2：`yaw` 速率 `dt` 取值错误

原 `control_poll_imu()` 中，当 `yawSampleUpdated=1` 时，传给 `ICM42688_UpdateYaw()` 的 `dt` 是按：

- `tickCount - imuPollLastTick`

来算的。

这实际上是“距离上一次轮询”的时间，而不是“距离上一次真实 `yaw` 样本更新”的时间。若若干次轮询都没有新的姿态样本，随后突然来了一个新样本，就会导致：

- `dt` 被低估
- `yawRate` 计算失真
- 连续性判断依据失真

本轮已在 `ControlSystem_t` 中新增：

- `imuYawSampleTick`

并在 `control_poll_imu()` 中改为：

- 按“上一拍 `yaw` 样本时间”计算 `dt`
- 在本拍成功更新 `yaw` 后刷新 `imuYawSampleTick`

对应修复文件：

- `Hardware/Control.h`
- `Hardware/Control.c`

### 根因 3：异常 `yaw` 更新的放行条件过宽

原 `ICM42688_UpdateYaw()` 对异常跳变只做：

- `fabs(dy) > BNO085_YAW_JUMP_REJECT_DEG`

才拒绝。

这意味着如果四元数解析错误导致的是“中等幅度但明显不合理”的跳变，则可能被放行。

本轮已补为联合约束：

- `fabs(dy) > BNO085_YAW_JUMP_REJECT_DEG`
- 或 `fabs(dy / dt) > BNO085_YAW_RATE_LIMIT_DPS`

任一成立都拒绝本次 `yaw` 更新，并保持上一拍 `yaw`。

### 本轮修改文件

- `Hardware/Control.h`
- `Hardware/Control.c`
- `Hardware/ICM42688.c`

修复后预期先改善：

- BNO 四元数解析错位导致的 `yaw` 突跳

## 第六阶段根因收敛：尾段 `txdrop` 负载收敛

### 新现象

在 `exp004` 中，前置静止段 `run=0` 已明显稳定，但实验结束后的尾段仍出现：

- `txdrop=12347`

这说明尾段观测中已经混入明显的串口发送过载因素，不能只继续盯 `yaw` 本体，还需要先收敛文本遥测负载。

### 负载来源定位

当前 FireWater 文本模式下：

- `HB` 本身为长文本
- `control_send_hb()` 每次还会附加一整行 `BNO ...` 调试信息
- 运行态还会附加 `samples:...`

上述文本叠加后，在尾段与 dump 相邻阶段容易把 `VOFA` 的 TX 环形缓冲打满，最终抬高 `g_vofaTxDropBytes`。

### 本轮最小降载修改

本轮不改控制主逻辑，只做观测链路减载：

1. `Hardware/Control.c`

- 保留运行态 `samples:...`
- 移除非运行态额外 `samples` 文本发送

2. `Hardware/BNO085_DebugSerial.c`

- 保留 `BNO` 调试输出能力
- 但按运行态做节流：
  - `run=1`：保守保留
  - `run=0`：进一步降频

### 目的

这一轮的目的不是直接“修复姿态”，而是先让：

- 尾段 `txdrop` 明显下降
- 原始日志不再大面积粘连
- 重新验证尾段 `run=0` 的 `yaw_jump` 是否仍然独立存在

若降载后尾段异常同步显著收敛，则说明此前尾段观测已被串口过载明显污染；若降载后异常仍独立存在，再继续回到 `yaw` 链路本体做更严格静止态保护。

## 第七阶段根因收敛：剥离 PC 端 `yaw_jump` 假阳性

### 新发现

在 `exp005` 中：

- 总 `yaw_jump` 从 `5` 进一步降到 `4`
- 尾段 `run=0` 只剩 1 个异常
- 且该异常点与上一拍运行态样本之间存在明显长时间空档

同时，尾段 `yaw` 已不是 `exp004` 中那种大幅摆动，而是快速收敛到约 `2.504`，`yr` 也只有极小值。

因此当前残留的尾段 `run=0` 异常，更像是：

- PC 端异常检测把“运行态最后一拍”与“很久之后的 idle 拍”直接当作连续样本比较
- 从而制造了 `yaw_jump` 假阳性

### 根因定位

`exp_runner.py` 中原 `detect_time_series_anomalies()` 的 `yaw_jump` 判定逻辑，只按相邻行比较 `yaw` 差值，没有同时检查：

- `run` 状态是否一致
- `tick` 间隔是否连续

这会把以下情形误判为真实 `yaw_jump`：

- `run=1 -> run=0` 状态切换
- 长时间空档后的后置 idle 段

### 本轮修正

在 `exp_runner.py` 中新增：

- `YAW_JUMP_MAX_TICK_GAP_MS = 1000.0`

并将 `yaw_jump` 判定修正为：

- 仅在 `prev_run == cur_run`
- 且 `0 < tick_gap <= YAW_JUMP_MAX_TICK_GAP_MS`

时，才允许按相邻样本 `yaw` 差值打 `yaw_jump`。

### 预期效果

修复后预期：

- 不再把实验结束后的尾段 idle 样本误判为运行过程中的 `yaw_jump`
- 能更干净地保留真正运行态的姿态异常
- 后续分析将更聚焦于真实 `run=1` 阶段的问题，而不是被尾段假阳性干扰

## 第八阶段根因收敛：起步反向脉冲与角度环导数踢穿

### 新发现

在 `exp006` 中，PC 端尾段 `run=0` 假阳性已经被剥离后，剩余异常全部集中在真实 `run=1` 阶段。

其中最关键的起点样本为：

- `tick=517387`
- `yaw=-4.540`
- `yr=-6.265`
- `pwm=-26`
- `L/R=-13/-19`
- `OL/OR=-23/-29`
- `el/er=21/30`
- `angleErr=1.228`
- `angleOut=-15.529`

这说明该拍并不是“航向差分把左右轮拉反”，而是**角度环基准输出 `pwmCore` 自己先被打成了负值**，随后双轮一起反向。

### 根因定位

`Control.c` 中角度环为：

- `derivative = (actualAngle - prevActualAngle) / dt`
- `angleOut = Kp * angleErr + Ki * angleI - Kd * derivative`

原实现存在两个问题：

1. 启动阶段 `anglePrevActual` 被重置为 `0.0f`

而不是当前真实角度，这会让起步后的首批有效姿态样本与 `0` 直接做差，放大导数项。

2. 角度环导数项完全不限幅

只要某一拍 `actualAngle` 突变，`-Kd * derivative` 就可能瞬间压过正向 `P` 项，把 `angleOut` 直接踢成负值。

这与 `exp006` 的双轮反向脉冲现象完全一致。

### 本轮修正

1. `Hardware/Control.c`

- 新增：`ANGLE_DERIVATIVE_LIMIT_DPS = 25.0f`
- 对角度环导数项做限幅

2. `Control_Start()` 初始化阶段

- 原先：`sys->anglePrevActual = 0.0f`
- 现改为：`sys->anglePrevActual = sys->sensedPitch - sys->angleZero`

即启动时直接把角度环上一拍角度初始化为当前真实角度，避免首拍导数失真。

### 预期效果

修复后预期优先改善：

- 起步阶段双轮同时反向脉冲
- 角度环导数项瞬时踢穿导致的 `pwm` 反号
- 由此诱发的起步阶段运行态 `yaw_jump`

## 第九阶段根因收敛：航向保持符号方向修正

### 新发现

在 `exp007` 中，起步反向脉冲已经消失，但现场现象变成了：

- 小车起步后明显向右转
- 甚至右转撞墙

日志与该现象一致：

- `tick=30439`：`yaw=8.318`，`OL/OR=18/24`
- `tick=30859`：`yaw=-13.370`，`OL/OR=18/28`

即当车辆已经发生明显偏航时，控制输出仍在继续给偏航同向一侧更大的 PWM。

### 根因定位

`control_apply_motor_output()` 中原航向误差定义为：

- `yawErr = wrap_deg180(sensedYaw - targetYaw)`

而差速分配为：

- `leftCore = pwmCore - diffPwm`
- `rightCore = pwmCore + diffPwm`

在当前“正 yaw 表示右偏/右转”的链路约定下，这一组合会导致：

- 当车辆右偏时，`yawErr` 为正
- `diffPwm` 为正
- 最终继续增加右轮、减小左轮

也就是把偏航误差进一步放大。

### 本轮修正

将航向误差改为：

- `yawErr = wrap_deg180(targetYaw - sensedYaw)`

保持原有差速混合方式不变，使其满足：

- 右偏时优先增左减右
- 左偏时优先增右减左

### 预期效果

修复后预期优先改善：

- 起步后持续右转
- 航向保持在偏差出现后继续“同向加力”的问题
- 因起步右偏带来的撞墙风险

## 第十阶段根因收敛：回退错误符号修正并延后航向介入

### 结果回看

第九阶段单独翻转 `yawErr` 符号后，`exp008` 结果明显恶化：

- `yaw_jump` 从 `2` 直接升到 `12`
- `yaw_min=-158.565`
- `yaw_max=176.402`
- 轨迹严重发散，已不属于“轻微偏航”，而是错误修正方向导致的强烈失稳

因此，第九阶段“单独翻转 `yawErr` 符号”的方向已被实验直接证伪。

### 重新收敛后的判断

结合 `exp007` 与 `exp008`：

- `exp007`：问题主要集中在起步早期，且恶化点出现在航向保持开始介入后
- `exp008`：单独翻转误差符号后直接变成强烈左转发散

这说明当前更稳妥的方向不是继续改误差符号，而是：

- 回退这次错误修正
- 优先延后航向保持默认介入时机，避免起步阶段使用尚未稳定的 `yaw` 做纠偏

### 本轮修正

1. `Hardware/Control.c`

  - `yawErr = wrap_deg180(sensedYaw - sys->targetYaw)`

2. 调整默认航向保持延迟：

- 原先：`STABLE_DEFAULT_HEADING_DELAY_MS = 400u`
- 现改为：`STABLE_DEFAULT_HEADING_DELAY_MS = 1200u`

### 预期效果

本轮目标不是立刻追求完美轨迹，而是先优先保证：

- 起步后不再立即撞墙
- 起步阶段不再过早使用不稳定 `yaw` 做强纠偏
- 后续再在更稳定的启动段上继续微调航向保持逻辑

## 第十二阶段根因收敛：避免 `yaw` 跳变拒绝后的长时间卡死

### 新发现

结合 `exp009`：

- 前段可以晃动直走
- 后段进入 `right_biased spin_turn`
- 同时 `yaw` 在后段长时间卡在同一数值附近，而右侧输出/编码器偏置仍持续存在

这说明问题不只是“偏右”，还存在更深一层的姿态链路异常：

- `yaw` 一旦进入异常拒绝分支，可能被长期锁在旧值
- 控制器随后基于陈旧 `yaw` 继续输出错误差速

### 根因定位

`ICM42688_UpdateYaw()` 原逻辑中，若：

- `fabs(dy) > BNO085_YAW_JUMP_REJECT_DEG`
- 或 `fabs(yawRate) > BNO085_YAW_RATE_LIMIT_DPS`

则直接：

- `data->yaw = data->prevYaw`
- `data->yawRate = 0`
- `return`

这会导致一个锁死模式：

- 一旦当前 `newYaw` 与旧 `prevYaw` 相差过大
- 本拍直接冻结
- 下一拍仍然拿旧 `prevYaw` 继续比较
- 若差值持续过大，就会连续拒绝，形成长时间卡死

### 本轮修正

将原先的“硬冻结拒绝”改为“限速跟踪恢复”：

- 超阈值时不再直接 `return`
- 改为按 `BNO085_YAW_RATE_LIMIT_DPS * dt` 计算允许最大步长
- 将 `dy` 限幅到该最大步长内
- 再用限幅后的 `dy` 更新 `newYaw` 与 `yawRate`

即使遇到异常大跳变，也不会再长期锁在旧 `yaw`，而是以受控速度逐步恢复跟踪。

### 预期效果

本轮优先验证：

- `exp009` 式的后段 `yaw` 卡死是否消失
- 后段 `spin_turn` 是否减弱
- `yaw_jump` 数量是否进一步下降

## 第十三阶段根因收敛：修正主循环时序，消除姿态相位滞后

### 新发现

在 `exp010` 中，上一轮“`yaw` 限速跟踪恢复”已经去掉了后段长时间卡死，但新的问题变成了：

- `yaw` 不再冻结
- 但进入了高幅左右翻摆
- `heading_variation` 很大，`yaw_jump` 反而回升

进一步检查 `Control.c` 后发现，当前控制时序存在明显相位滞后：

- `Control_TimerTickISR()` 中先执行 `control_speed_loop()`
- 再执行 `control_angle_loop()`
- 而 `control_poll_imu()` 却放在 `Control_Background()` 的后面才执行

这意味着本拍控制输出使用的其实是上一拍甚至更旧的姿态数据。

### 根因判断

对于低速小车尤其是当前这种容易左右摆动的阶段：

- 若 `heading` 纠偏天然滞后一拍
- 就会把本来应该阻尼的控制，变成加相位差的左右翻摆

这与 `exp010` 中“进入控制后姿态大幅左右切换”的现象高度一致。

### 本轮修正

将 `IMU` 轮询从 `Control_Background()` 前移到 `Control_TimerTickISR()` 中：

- 先执行 `control_poll_imu()`
- 再执行速度环与角度环

并移除 `Background` 中原有的重复 `IMU` 轮询。

### 预期效果

本轮优先验证：

- 控制输出是否改为使用本拍最新姿态
- `heading` 左右翻摆是否下降
- `wobbling_straight_then_spin_turn` 是否减弱或后移

## 第十四阶段根因收敛：起步参数与航向参数最小解耦

### 代码审查结论

在继续扫参与复测后，逐步确认当前不仅存在“参数值不合适”的问题，也存在“参数作用域互相缠绕”的问题。

最关键的两处耦合为：

1. `SIV` 与 `heading` 启用条件存在隐藏耦合

- 原先 `headingEnabled` 条件中包含：
  - `abs(actualSpeed) >= speedIEnableSpeed`
- 而 `speedIEnableSpeed` 正是由 `#SIV=` 设置

这意味着：

- 用户以为在调“速度积分启用阈值”
- 实际上也同时在调“航向环什么时候允许启用”

2. `startupBias` 与 `heading` 会在同一输出层直接叠加

- 原先先做 `heading` 差速
- 随后无条件再叠加 `startupBias`

这会导致：

- `SBF/SBV` 与 `HDT`、航向差速同时改左右输出
- 调一个参数时，另一个链路也在同时参与，造成现象不易解释

### 本轮整改

在 `Hardware/Control.c` 中执行两项最小解耦：

1. 将 `headingEnabled` 从：

- 运行态
- 正常模式
- `abs(actualSpeed) >= speedIEnableSpeed`
- 延迟达到 `HDT`

改为：

- 运行态
- 正常模式
- `abs(pwmCore) >= HEADING_ENABLE_PWM_THRESHOLD`
- 延迟达到 `HDT`

也即：

- `SIV` 只再控制速度积分何时介入
- 不再偷偷影响航向环启用时机

2. 将 `startupBias` 改为仅在 `heading` 未启用时生效

- 原先：始终计算并叠加 `startupBias`
- 现改为：`headingEnabled ? 0 : control_calc_startup_bias(...)`

也即：

- 起步偏置只负责起步前段
- 航向环启用后不再与其叠加“抢方向”

### 预期效果

本轮优先验证：

- `SIV` 调整是否只影响速度积分，不再改变航向启用时机
- `SBF/SBV` 的作用是否更集中在起步前段
- `HDT` 与航向差速的效果是否更独立、更易解释
