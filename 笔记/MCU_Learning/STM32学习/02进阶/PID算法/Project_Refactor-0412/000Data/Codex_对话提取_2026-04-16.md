## 阶段 4：持续收敛锐角退出

### 调整链路

后续围绕锐角退出、重入和恢复态，逐步做了这些修改：

- `TRACK_ACUTE_MIN_YAW`
  - `30° -> 7°`
- 退出逻辑
  - 从二次 `read_sensor_bits()` 改成复用当前周期 `g_lineTrack.sensorBits`
  - 退出观察区从 `S4|S5` 放宽到 `S3~S6`
- 锐角退出后加重入锁定
  - `TRACK_ACUTE_REARM_MS = 300`
- 增加 `acuteState` 调试
  - `acuteState`
  - `acuteYawDelta`
  - `acuteRearmTick`

### 实测演化

- 一开始判断是“退出过晚”
- 加入真实内部状态后发现：
  - 有些看起来像锐角转向的段，未必真进了锐角状态机
- 拉长到 `8s` 后确认：
  - 真实 `acuteState=1 -> 2 -> 0` 已经发生
  - 退出 yaw 不再拖到 `50°`

### 中期结论

- “退不出来”已不再是主问题
- 新问题变成：
  - 刚退出锐角，普通巡线 PD 立刻把车拉回去

## 阶段 5：锐角恢复态与 handoff 修复

### 用户观察

- 小车像是想转锐角，但马上又摆回去

### Codex 处理

- 实现 `acute recover` 恢复态：
  - 新增 `LT_ACUTE_RECOVER`
  - 新增 `acuteRecoverStartTick`
  - 新增 `acuteRecoverStableCount`
- 参数：
  - `TRACK_ACUTE_RECOVER_HOLD_MS`
  - `TRACK_ACUTE_RECOVER_TIMEOUT_MS`
  - `TRACK_ACUTE_RECOVER_STABLE_COUNT`
- 退出锐角后不立刻交回普通 PD

### 后续继续优化

- 恢复态从“等速直行”改成“轻微同向弧线恢复”
- 然后又把恢复态退出条件改成：
  - 方向感知
  - 居中约束
- 再把“恢复态超时后，不允许盲目放权回 PD”改成：
  - 超时后转入定向找线

### 结论

- 锐角这条链路最终收敛到：
  - 触发正常
  - 退出不再明显过迟
  - handoff 明显更平顺
- 锐角后来被认为“基本过关”

- 后续仍有微调，但整体逻辑已经分离成功

## 阶段 7：通用 `CSR` 找线链继续收敛

### 问题

- 某些弯道不是锐角，也不是 `R90`
- 会走到 `CSR`
- 出现“明明已经扫到线了，但还是继续转”的现象

### Codex 处理

- 先补了更多遥测字段：
  - `st`
  - `cd`
  - `cy`
  - `cb`
  - `cm`
  - `cg`
  - `ch`
- 基于日志发现：
  - 不是“看到了线却不退出”
  - 而是“`cg=0`，最小接受角没到”
- 因此微调：
  - `TRACK_CORNER_MIN_YAW`
  - `TRACK_CORNER_ACCEPT_LATCH_YAW`
- 给 `CSR` 也加了：
  - 目标线锁存
  - 当前帧方向一致性约束
  - 再后来放宽成“只屏蔽强反向线型”

### 标志性结果

- 某个长期过转的弯道：
  - `max cy ≈ 50.4°`
  - 后面收敛到 `≈ 28.8°`
  - 再到 `≈ 25.2°`

### 结论

- `CSR` 这条链路经过多轮小修后，明显压住了过转

## 阶段 8：交叉线误判为左转

### 用户问题

- 有一个交叉线区域
- 小车在这里会误判为左转
- 需求是：
  - 保持直行绕过去
  - 不影响其他锐角、直角、普通找线逻辑

### Codex 方案

- 不恢复旧的全局交叉口逻辑
- 在当前状态机内加一个专用的交叉绕过态：
  - `CRS`
- 触发思路：
  - 左右两侧同时有分支证据
  - 中间仍然在主线
  - 亮灯数达到阈值

### 实现内容

- 新增：
  - `crossBypassActive`
  - `crossBypassUntilTick`
- 新增参数：
  - `TRACK_CROSS_BYPASS_MIN_COUNT`
  - `TRACK_CROSS_BYPASS_HOLD_MS`
- 绕过期间：
  - 屏蔽 `acute / R90 / CSR`
  - 不因为 `bits==0` 就进入 `cornerTurning`
  - 只用 `S3~S6` 计算位置
- 串口状态新增：
  - `st=CRS`

### 状态

- 代码和固件已经加入 `CRS` 绕过态
- 但用户后续现场反馈是：
  - 交叉线当时仍未完全修好
- 这说明 `CRS` 是当前交叉问题的主修复方向，但那一轮还没完全收口

## 阶段 9：启动异常诊断

### 用户问题

- `OLED` 一直卡在 `System Ready`
- 小车按 `KEY` 没反应

### Codex 分析

- `System Ready` 只在 `BspOled_Init()` 写一次
- 如果主循环已经开始，即使不跑，也应该很快刷新成 `STOP`
- 所以如果一直停在 `System Ready`：
  - 高概率根本没进入 `while(1)`

### 核心推断

- `KEY` 不是 EXTI 中断
- 它依赖：
  - `TIM4 -> Main_TimerTickISR -> BspKey_Tick`
  - 主循环里的 `process_key_event()`
- 但 `Timer_Init()` 在 `BNO085_Init()` 后面
- 所以如果卡在 `BNO085_Init()`：
  - OLED 保持初始化字样
  - KEY 轮询根本没跑起来

### 诊断结论

- 最高概率根因：
  - 卡在 `BNO085_Init()`
- 次高概率：
  - 启动早期 HardFault/BusFault 复位循环

### 后续约定

- 用户要求加入三条诊断补丁：
  - 提前 `Timer_Init()`
  - OLED 显示 `IMU init stage/address`
  - 读取 `FaultTrace_GetAndClearCode()`

## 当前代码侧沉淀下来的关键状态字符串

- `TRK`：普通循迹
- `AWN`：锐角时间窗
- `ATN`：锐角转弯
- `ARC`：锐角恢复

- `R90`：直角专用处理
- `CRS`：交叉直行绕过

## 当前对话中落下来的核心结论

### 1. 锐角

- 已经基本过关
- 真正起作用的是：
  - 退出门槛下调
  - 当前周期 sensorBits 复用
  - 恢复态 handoff

### 2. 直角

- 已经从锐角链中拆出来
- `R90` 是正确方向
- 后续是微调 accept 条件和转向力度

### 3. 通用找线

- `CSR` 过转问题主要靠：
  - `accept latch`
  - 当前帧方向一致性
  - `TRACK_CORNER_MIN_YAW`
  收敛

### 4. 交叉线

- 已经进入结构化修复阶段
- `CRS` 是为“交叉直穿而不是误左转”专门引入的绕过态
- 但最后一轮用户反馈说明它当时还没完全收口

### 5. 启动异常

- `OLED` 卡在 `System Ready`
- `KEY` 没反应
- 代码层面最可疑的还是：
  - `BNO085_Init()` 阻塞在主循环之前
